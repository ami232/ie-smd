    Group project¶

    Draft

    This page is a draft and may change before it is published.

    Weight: 30 % of the final grade, with individual assessment. Teams: the nine teams set by the programme (Blackboard → Groups).

    The idea¶

    Your team builds one product: a small financial application of the kind a real company would use. Each member builds one module of it, and the team puts the modules together into one application that runs in the cloud.

    You already know how to build a module: it is the application you build in your own repository, lab by lab, along the same path as ledger. A Python package with a database, a REST API, tests, a web page, containers and a deployment on Azure. The group project adds what you can only learn in a team: agreeing on how the parts fit, reviewing each other's code, integrating, and running one system together.

     member 1 ─ module ─┐
 member 2 ─ module ─┤
 member 3 ─ module ─┼──▶  one product: one database, one API, one web frontend,
 member 4 ─ module ─┤                  Docker Compose, CI, deployed on Azure
 member 5 ─ module ─┤
 member 6 ─ module ─┘

    Choose a theme¶

    Each team chooses one theme, and no two teams take the same one: first come, first served. You can propose your own theme if it splits into one module per member in the same way.

    Theme Modules
    Freelancer finance clients · time tracking · invoices · payments received · expenses · tax estimator · cash-flow report
    Shared household members · shared expenses and splits · settle-up · budgets · subscriptions · savings goals · bills calendar
    Small shop products · inventory · sales · suppliers and purchases · customers · cash flow · price margins
    Investment club members · contributions · holdings · trades · dividends · performance · voting on proposals
    Micro-lending borrowers · loan applications · loans and schedules · repayments · late fees · risk score · portfolio report
    SME back office employees · payroll · expense claims · leave · departments and budgets · invoices to pay · headcount cost
    Trip planner travellers · trips · bookings · shared costs · currency conversion · budget · settle-up
    Crowdfunding campaigns · backers · pledges · reward tiers · payouts · fees · campaign analytics
    Insurance claims policyholders · policies · premiums · claims · claim assessment · payouts · loss ratio report
    Personal wealth accounts · net worth · goals · recurring income and expenses · retirement projection · debts · rebalancing

    Your module¶

    Every member owns one module, and builds it in their own repository during the labs. A module has:

    • one main entity (an invoice, a loan, a booking…), stored in the database, which the API can create, read, update and delete;
    • one calculated result: a balance, a report, a forecast, a score;
    • tests for its logic and its endpoints;
    • one page in the web frontend.

    Amounts of money are Decimal in Python and NUMERIC in the database.

    Your shared job¶

    On top of your module, each member is responsible for one part of the shared product. With six members, the team covers six of these; with seven, all of them:

    Shared job Responsible for
    Continuous integration the GitHub Actions workflow: Ruff and the tests on every pull request
    Containers and configuration the Dockerfile, Docker Compose, settings from environment variables, .env.example
    Cloud deployment the Azure resources, the deployment and its cost
    Frontend shell and dashboard the common layout, navigation and the dashboard that combines the modules
    Database the shared database setup, the models' common base and the sample data
    Code review the review rules, and that every pull request is reviewed
    Documentation and board the README, the architecture diagram, and the issues and project board

    Being responsible doesn't mean doing it alone: it means making sure it is done, and being able to explain it.

    How the team works¶

    • One team repository on GitHub, in which every member is a collaborator.
    • Every change goes through a pull request, reviewed and approved by another member before it is merged into main, with a merge commit.
    • Tasks are GitHub issues, on a project board, assigned to a member.
    • A conventions agreement in the README, written early: the same stack, package names, API routes under /api/<module>, and how money and dates are stored. It is what lets modules written separately fit together.
    • At least one feature crosses modules: a dashboard that combines them, or a module that uses another's API.

    Assessment¶

    The team grade assesses the product: what works in the demo, how the modules are integrated, containers, CI and cloud, the process (issues, reviewed pull requests, documentation) and the presentation.

    Your individual grade is the team grade adjusted by your own part:

    • your module in the team's product;
    • your shared job;
    • your pull requests and your reviews, as the repository's history shows them;
    • your answers to questions about the code, any part of it;
    • a confidential peer assessment by your teammates.

    A member who doesn't contribute can get a much lower grade than the team; a member who carries the team gets a little more.

    Using AI¶

    AI is allowed under the course rules. You answer for every line of your module and of your pull requests, and in the question round you may be asked about any part of the code.
