# Dependencies and the lockfile

> ℹ️ **What you need first**
>
> Virtual environments, `pyproject.toml` and the basic uv commands, from [Python projects and environments](../03-python-uv/python.md), and the `ledger` project from [Lab 3](../03-python-uv/lab.md).

A project needs four things: a declared Python version, its own environment, a standard way to run it, and **a precise list of the libraries it uses**. The first three were set up in [session 3](../03-python-uv/python.md#from-a-script-to-a-project). So far `ledger` only uses Python's standard library, so the list is empty. The moment it needs a library from PyPI, the project needs that fourth thing, and this page explains how it works.

## Direct and transitive

The libraries your code imports are its **direct dependencies**. They have dependencies of their own, which you also need: these are **transitive** dependencies. In [Lab 4](lab.md), `ledger` depends on one library, `rich`, which draws tables in the terminal. But installing it brings four packages:

```text
ledger v0.1.0
└── rich v15.0.0
    ├── markdown-it-py v4.2.0
    │   └── mdurl v0.1.2
    └── pygments v2.21.0
```

A typical web application has a dozen direct dependencies and a hundred transitive ones. Any of them can change.

## Version constraints

You declare a direct dependency with a **constraint**, a range of acceptable versions, such as `rich>=15.0.0`. Constraints rely on a convention called **semantic versioning**: in `MAJOR.MINOR.PATCH`, a new **major** version may break your code, a **minor** one adds features without breaking anything, and a **patch** only fixes bugs. Many projects follow it, some loosely.

| Constraint | Means |
|---|---|
| `rich` | any version |
| `rich>=15.0` | 15.0 or newer, including a future 16.0 that may break things |
| `rich>=15.0,<16` | any 15.x: features and fixes, no breaking changes |
| `rich==15.0.0` | exactly that version |

Constraints alone are not enough for reproducibility. `rich>=15.0` installs today's newest version today and a different one next month, and the same goes for every transitive dependency. Two people installing the "same" project a month apart can get different code.

## The lockfile

> 📘 **Definition: lockfile**
>
> A **lockfile** records the exact version of **every** package the project needs, direct and transitive, with a hash of each file to verify the download. It is generated by a tool from the constraints, committed to the repository, and used to install exactly the same packages everywhere.

The two files have different jobs. **`pyproject.toml` says what the project accepts** (its constraints). It is written by people. **`uv.lock` says what the project uses** (the resolved versions). It is written by the tool. Changing a dependency means editing the constraints, usually with `uv add` or `uv remove`, and letting the tool update the lock. When you want newer versions, you upgrade deliberately (`uv lock --upgrade`), run the tests, and commit the new lockfile, so the change is visible and reviewable.

## uv commands for dependencies

| Command | Does |
|---|---|
| `uv add rich` | adds a dependency: updates `pyproject.toml`, `uv.lock` and `.venv` |
| `uv add --dev ruff` | adds a dependency only for development (tests, linters), in its own group |
| `uv remove rich` | removes a dependency |
| `uv sync` | makes `.venv` match `uv.lock` exactly (installs, upgrades, removes) |
| `uv tree` | shows the dependency tree |
| `uv lock --upgrade` | resolves again with the newest versions the constraints allow |

`uv run` also syncs the environment before running, so after a teammate changes the lockfile, your next `uv run` installs what changed. Together, `.python-version`, `pyproject.toml` and `uv.lock` describe layers 4 and 5 of the environment completely. Anyone who has uv can rebuild them identically, which is exactly the "automate it" level of reproducibility from [session 1](../01-dev-environments/environments.md#reproducibility).

## Common mistakes

- **Not committing `uv.lock`.** Without it, the project is not reproducible: every installation resolves the constraints again.
- **Editing the lockfile by hand.** It is generated. Change the constraints, with `uv add` or `uv remove`, and let uv update it.
- **Constraints that are too loose or too tight.** With `rich` alone, any future version is accepted, even one that breaks the code. With `rich==15.0.0`, the project never gets bug fixes, and it can't be installed next to another library that needs a newer `rich`. A lower bound such as `rich>=15.0.0`, which is what `uv add` writes, plus the lockfile, is the usual choice.

> ✅ **Key takeaways**
>
> - **Direct** dependencies are the ones your code imports; they bring their own **transitive** dependencies.
> - `pyproject.toml` declares the direct dependencies with **constraints**, a range of acceptable versions. It is written by people.
> - The **lockfile**, `uv.lock`, pins **every** package to an exact version, with hashes. It is written by uv. Commit both files.
> - `uv add` and `uv remove` change the constraints and the lockfile together; `uv sync` makes `.venv` match the lockfile.

## Exercises

**1.** In the dependency tree above, which dependencies are direct and which transitive? If `rich` stopped needing `pygments` in a future version, what would you have to change in `pyproject.toml`?

<details>
<summary>✅ <b>Solution</b></summary>

`rich` is the only direct dependency of `ledger`. `markdown-it-py`, `mdurl` and `pygments` are transitive: `ledger` gets them because `rich` needs them. You wouldn't change anything in `pyproject.toml`, because `pygments` is not listed there. After upgrading `rich` (`uv lock --upgrade-package rich`), uv would drop `pygments` from `uv.lock`, and `uv sync` would uninstall it from `.venv`.

</details>

**2.** Your `pyproject.toml` says `pandas>=2.0`. Today, uv locks pandas 2.3.3. Six months later a teammate clones the repository. *(a)* With the lockfile committed, which version does `uv sync` install for them? *(b)* And if the lockfile was not committed?

<details>
<summary>✅ <b>Solution</b></summary>

- *(a)* Exactly **2.3.3**, the version in `uv.lock`, whatever is newer on PyPI. That is the point of the lockfile.
- *(b)* uv resolves the constraint again, so they get **the newest version that satisfies `>=2.0`** six months later, maybe 2.4 or even a 3.0 that breaks the code. The two of you would be running different code without knowing it.

</details>
